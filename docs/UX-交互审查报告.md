# 用户交互逻辑审查报告

> 审查对象：campus-recruit 前端（`index.html` 4032 行 + `js/cloud-sync.js`）
> 审查范围：交互流程 / 操作反馈 / 状态提示 / 异常处理 / 易用性
> 审查日期：2026-09-12

## 结论摘要

本次审查共识别 **14 项问题**，其中 **2 项为 P0 级**（数据正确性缺陷，与产品设计意图直接冲突），**4 项 P1 级**（反馈与状态缺失），**5 项 P2 级**（易用性），**3 项 P3 级**（细节）。

最严重的发现是一个**数据丢失缺陷**：未登录用户的投递记录不会写入本地存储，但界面会显示成功提示。该问题与代码库中已有的多处设计意图（未登录专属存储键、登录后合并、离开页面提醒）相互矛盾。

---

## P0 级问题（数据正确性）

### P0-1 未登录投递记录不落盘，且提示虚假成功

**现象**

未登录用户点击「记录投递」后，界面提示"已记录 N 条投递"，但刷新页面后记录全部消失。

**证据链**

| 位置 | 代码 | 说明 |
|------|------|------|
| `index.html:3083` | `if (!currentUser) { showLoginReminder(_do); return; }` | 未登录时弹提醒，但用户可点「我已知晓」继续执行 |
| `index.html:3408` | `showLoginReminder` 的 dismiss 分支直接 `onProceed()` | 继续执行 `_doRecordSelected()` |
| `index.html:2782` | `function saveProgress() { if (!currentUser) return; ... }` | **未登录直接返回，不写 localStorage** |
| `index.html:2792` | `showToast(added > 0 ? \`已记录 ${added} 条投递\` : ...)` | 仍提示成功 |

**矛盾点（需要决策）**

代码库中存在两个平行函数，行为不一致：

```js
function saveProgress() { if (!currentUser) return; localStorage.setItem(_pkey(), ...); }  // 有门槛
function saveOffers()   { localStorage.setItem(_okey(), JSON.stringify(offers)); }          // 无门槛
```

同时存在三处明确指向"支持未登录本地存储"的设计：

1. `_pkey()` / `_okey()`（行 3468）为未登录状态专门返回 `campus_recruit_progress` / `campus_recruit_offers`
2. `_hasLocalData()`（行 3440）主动检查未登录键下的数据，供 `beforeunload` 提醒使用
3. `mergeLocalToUser()`（行 3445）在登录时把未登录数据合并进用户账户

因此可以判定：**`saveProgress()` 的 `if (!currentUser) return;` 是缺陷，而非设计**。代价是：游客模式记录投递 → 数据丢失 → `beforeunload` 提醒永不触发（因为 localStorage 本来就是空的）→ 登录后 `mergeLocalToUser` 也无数据可合并。

**优化建议**

1. 删除 `saveProgress()` 中的 `if (!currentUser) return;`，与 `saveOffers()` 对齐
2. 若产品确实要求"必须登录才能记录"，则应改为：未登录时**不执行写入**，并明确提示"请先登录后记录"，而不是伪造成功
3. 两种方案不可混用 —— 建议先由产品确认游客模式是否受支持，再统一实现

**预期收益**

- 消除游客模式下的数据丢失路径（影响所有未登录用户）
- 修复 `beforeunload` 提醒与 `mergeLocalToUser` 的失效逻辑，使"登录后自动合并本地数据"真正可用
- 消除界面提示与实际状态不一致引发的信任损耗

### P0-2 登录/注册流程缺少异常捕获与提交态

**现象**

网络异常时登录请求抛出的 Promise rejection 无人处理；请求进行中按钮无 loading，用户可重复点击。

**证据**

```js
async function loginWithEmail() {
  ...
  const { data, error } = await sb.auth.signInWithPassword({ email, password });  // 无 try/catch
  ...
  showToast('登录成功，数据已同步');   // 但 syncAndRender 内部失败仅 console 警告
}
```

- `index.html:loginWithEmail` / `doRegister` 全程无 `try/catch`，网络中断时异常向上冒泡至全局
- 全文件 `grep -c "disabled = true|isSubmitting"` 结果为 **0** —— 无任何防重复提交机制
- 成功提示"数据已同步"早于实际同步结果（`syncAndRender` 内部 `catch` 只弹警告），构成误导

**优化建议**

1. 提交时置按钮 `disabled` + loading 文案（"登录中…"），`finally` 中恢复
2. 外层包裹 `try/catch`，网络异常统一提示"网络异常，请稍后重试"
3. 同步结果与登录成功分离提示：先"登录成功"，同步失败时追加"云端同步失败，本地数据已保留"（避免虚假成功）

**预期收益**

- 消除重复提交导致的并发请求（登录、注册、保存各一处）
- 网络异常场景从"静默失败"变为"明确可感知"
- 消除"数据已同步"的虚假承诺

## P1 级问题（反馈与状态）

### P1-1 Toast 单例且定时器不清理，连续操作时提示互相覆盖

**现象**：快速连续操作（如批量修改多行进度）时，后一条提示会提前消失或覆盖前一条。

**证据**

```js
function showToast(msg, duration) {
  const t = document.getElementById('toast');
  t.textContent = msg;
  t.classList.add('show');
  setTimeout(() => t.classList.remove('show'), duration || 2500);  // 无定时器句柄，无法取消
}
```

单例 DOM + 无句柄的 `setTimeout`：第 N 次调用会在第 N-1 次的定时器到期时被强制隐藏。批量修改进度（`updateStage` 已加 Toast）场景下必然复现。

**优化建议**：保存定时器句柄，新调用前 `clearTimeout`；或改为支持堆叠的 Toast 容器（最多 3 条）。

**预期收益**：提示可读性提升，消除"提示闪一下就不见"的困惑。

---

### P1-2 云端删除失败静默

**现象**：删除记录后界面显示"已删除"，但云端数据可能仍存在，下次同步后记录"复活"。

**证据**

```js
async function deleteFromCloud(table, ids) {
  try { await sb.from(table).delete().in('id', ids); }
  catch (e) { console.error(...); }   // 仅控制台输出，无用户提示
}
```

对比 `syncToCloud` / `syncFromCloud` 均会 `showToast` 报错，此处为唯一静默路径。触发条件：删除后网络中断、token 过期、RLS 拒绝。

**优化建议**：`catch` 中追加用户提示（"云端删除失败，本地已删除，将在下次同步重试"）；或将失败项写入待重试队列。

**预期收益**：消除"删除后又出现"的诡异体验，降低用户对数据一致性的疑虑。

---

### P1-3 同步错误信息笼统，无法区分故障类型

**证据**：`cloud-sync.js` 中三处错误提示均为"数据同步失败，请检查网络"。实际可能是网络不可达、token 过期（需重新登录）、RLS 权限拒绝 —— 三者的用户应对方式完全不同。

**优化建议**：按错误特征分流提示：
- 网络类（`Failed to fetch` / timeout）→ "网络异常，请检查连接"
- 认证类（`JWT expired` / 401）→ "登录已过期，请重新登录"
- 权限类（403 / RLS）→ "无权限同步该数据"

**预期收益**：用户可自助解决约 2/3 的同步失败场景，减少无效刷新。

---

### P1-4 行内编辑与结构变更缺少反馈闭环

**现象**

- 备注编辑（`updateNote`）保存后无任何提示，用户不确定是否已保存
- 手动添加/编辑弹窗提交后关闭弹窗，但无字段级错误定位（依赖 Toast 逐条提示）

**优化建议**：备注保存后显示一次轻量反馈（"已保存"微提示或输入框边框闪烁）；弹窗内校验失败时聚焦到首个错误字段。

**预期收益**：消除"改了但不确定存没存"的焦虑，减少重复操作。

## P2 级问题（易用性与效率）

### P2-1 零键盘支持

**证据**：全文件 `grep -c "keydown|Escape|Enter"` 结果为 **0**。

现状影响：所有弹窗（登录/注册/添加/编辑/时间线/确认）只能鼠标点击关闭；表单无法回车提交；下拉筛选无键盘导航。

**优化建议**

1. 全局 `keydown` 监听：`Escape` 关闭最上层弹窗/抽屉/下拉
2. 表单输入框 `Enter` 触发提交（登录/注册/添加/编辑）
3. 自定义下拉支持 `↑/↓` 移动、`Enter` 选中

**预期收益**：重度用户操作效率提升；满足 WCAG 2.1 键盘可达性要求（当前不达标）。

---

### P2-2 数据加载失败无重试入口

**证据**

```js
.catch(e => {
  document.getElementById('loading').innerHTML = '<p style="color:#e74c3c">数据加载失败，请检查网络后刷新页面</p>';
});
```

超时分支同此（行 2019-2024）。失败后用户唯一出路是手动刷新整页。

**优化建议**：错误态渲染"重试"按钮，直接调用 `loadData()`；同时把硬编码 `#e74c3c` 替换为设计 token `var(--danger)`。

**预期收益**：失败恢复成本从"刷新整页 + 重新筛选"降至"点击重试"，并保持视觉体系一致。

---

### P2-3 导入语义不清，且不报告跳过数量

**证据**

```js
showToast(`已导入 ${added} 条记录`);   // 未告知跳过多少条、为何跳过
```

两个问题：
1. 导入是**合并**语义（按 `company+position+applyDate` 去重后追加），但用户从"导出备份"的语境出发，通常预期"恢复备份"（覆盖）。语义未被说明。
2. 跳过数量不可见 —— 违反"跳过记录时数量与原因必须展示"的原则。

**优化建议**
- 导入前提示当前模式（"导入将合并到现有 N 条记录，重复项自动跳过"）
- 完成后报告："已导入 X 条，跳过 Y 条重复"
- 提供"覆盖导入"选项（可选，需二次确认）

**预期收益**：消除导入结果的心理预期偏差，使数据合并过程可审计。

---

### P2-4 破坏性操作无撤销

**证据**：`deleteRecord` / `batchDeleteProgress` / `deleteOffer` / `batchDeleteOffers` 仅有一次确认弹窗，确认后立即删除，无 undo。

**权衡**：引入完整撤销栈成本较高。建议采用**轻量方案**：Toast 附带"撤销"按钮，保留最近一次删除的数据副本（内存中保存 10 秒）。

**预期收益**：误删恢复率显著提升，尤其批量删除场景（一次误操作可能损失数十条记录）。

---

### P2-5 记录投递时重复项无明细提示

**证据**

```js
const exists = progressRecords.some(r => r.company === job.company && r.position === job.positions);
if (exists) return;   // 静默跳过
...
showToast(added > 0 ? `已记录 ${added} 条投递` : '选中的记录已存在');
```

批量记录时若部分重复、部分新增，用户只知道"记录了 N 条"，不知道哪些被跳过。另外去重键采用 `positions` 全字符串比对，同公司多岗位合并展示时可能产生误判。

**优化建议**：提示改为"新增 X 条，跳过 Y 条（已存在）"；去重键建议与导入保持一致（`company+position+applyDate`）。

**预期收益**：批量操作结果可核对，降低"为什么没记录上"的困惑。

## P3 级问题（细节）

| 编号 | 问题 | 建议 | 预期收益 |
|------|------|------|----------|
| P3-1 | 空状态无操作入口（进度页仅文字"还没有投递记录，从招聘岗位页面选择记录或手动添加"） | 空状态内嵌两个快捷按钮：「去挑选岗位」/「手动添加」 | 减少空状态下的迷失感，缩短首次使用路径 |

## 优先级与实施建议

**建议实施顺序**

1. **立即修复（P0）**：P0-1 数据丢失（需先与产品确认游客模式定位）、P0-2 登录异常处理
2. **本迭代（P1）**：Toast 单例、删除失败提示、同步错误分流、编辑反馈闭环
3. **下迭代（P2）**：键盘支持、失败重试、导入语义、撤销机制、去重提示
4. **按需（P3）**：空状态引导、重置入口、色值统一

**需要人类决策的冲突点**

`saveProgress()` 与 `saveOffers()` 的登录门槛不一致。两条路线互斥：

- **路线 A（推荐）**：未登录允许本地存储 → 删除 `saveProgress` 的 `currentUser` 判断，与 `saveOffers` 对齐。理由：与已有三处设计意图一致，且 `beforeunload` 提醒、`mergeLocalToUser` 合并逻辑均依赖此行为。
- **路线 B**：强制登录才能记录 → 需同时移除 `_pkey()`/`_okey()` 的未登录分支、`_hasLocalData()`、`mergeLocalToUser()` 的本地合并逻辑，并修改提醒弹窗文案。

在决策前，不宜混合两套模式。
